# Лабораторна робота №7
Аудит продуктивності каталогу репетиторів.

## Умови
Apple M4 Pro, 24 ГБ RAM, macOS 26.6.2. Chrome 157.0.8103.40, екран 1440×1000, DPR 1.
Окремі incognito-контексти headless Chrome без розширень. CPU 4×; мережа: завантаження 10 Мбіт/с, відправлення 5 Мбіт/с, затримка 40 мс.
Заміри зроблено на production-збірці: npm run build, npm run preview. Кеш для завантаження вимкнено. Дії записано після завантаження зображень; підготовка сторінки не входить у замір.

Кожне число — медіана трьох запусків. Усі результати є в [measurements.json](report/measurements.json).
Performance і Network записано через Chrome DevTools Protocol, трейси переглянуто в Performance. Lighthouse 13.6.0: Desktop, DevTools throttling. React Profiler використано в dev-режимі через тимчасові обгортки Profiler, зі StrictMode. У production цих обгорток немає.

Початкова версія — d8ebd59. Пошук: послідовно ввести «математика», пауза 100 мс після кожного оновлення. Обрані: натиснути сердечко першої картки. Скрол: почати з 700 px, зробити 12 кроків по 150 px з паузами 80 мс.

1. Компаратор багато разів рахував оцінку того самого репетитора. Тепер спочатку рахую оцінки, потім сортую готові значення. Порядок рекомендацій збережено. Скріншоти: [до](report/01-scores-before.png), [після](report/01-scores-after.png). Трейси: [до](report/01-scores-before.json), [після](report/01-scores-after.json).

2. Клік по сердечку запускав перерахунок списку й рендер усіх карток. Додав useMemo, useCallback і memo та стабільні обробники. React Profiler показав 2000 → 1 оновлену картку в усіх трьох запусках. Оновлення «Читати далі» також враховує вибір картки. Скріншоти: [до](report/02-renders-before.png), [після](report/02-renders-after.png). Трейси: [до](report/02-renders-before.json), [після](report/02-renders-after.json). [Дані Profiler](report/react-profiler.json).

3. Код змінював клас опису, читав висоту й повторював це для наступної картки. Браузер багато разів перераховував верстку. Тепер читання та зміни згруповано, події скролу об'єднано через requestAnimationFrame. Кількість Layout зменшилась зі 198 до 28. Скріншоти: [до](report/03-layout-before.png), [після](report/03-layout-after.png). Трейси: [до](report/03-layout-before.json), [після](report/03-layout-after.json).

4. Усі фото завантажувались одразу, місце під картинки не резервувалось. Додав width, height, loading="lazy" для фото та високий пріоритет банера. CLS завантаження зменшився з 0.581 до 0.000. Фото залишились доступні при прокрутці. Скріншоти: [до](report/04-images-before.png), [після](report/04-images-after.png). Трейси: [до](report/04-images-before.json), [після](report/04-images-after.json).

## Що не змінював
- buildSubjectOptions: 12 предметів, медіана 0.055 мс на виклик. Ланцюжок map/reduce не став вузьким місцем.
- Послідовні виклики довідників: медіана 0.9 мс. HTTP-запитів немає, дані готуються локально.

Ці додаткові заміри також зроблено в Chrome при CPU 4×. Для короткої функції — 200 повторів у кожному з трьох запусків.

## Перевірка
Regression-тест у src/__tests__/Catalog.test.js перевіряє порядок рекомендацій і кількість розрахунків. На початковому коді для 40 репетиторів було 320 викликів замість 40 — [лог падіння](report/regression-before.txt). Після виправлення обидва тести проходять — [лог](report/regression-after.txt).

Перевірено пошук, порожні результати, фільтри, сортування, збереження обраних після перезавантаження, деталі, Escape, «Читати далі» та запис на заняття. Production-збірка проходить, помилок JavaScript під час перевірки немає.
